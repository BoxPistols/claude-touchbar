# Claude Code CLI × Touch Bar 統合設計書

対象: ターミナル（iTerm2メイン）で動くClaude Code CLIのセッション状態をBetterTouchTool経由でTouch Barに表示・操作する仕組み。
検証環境: macOS 26.6 / BTT 6.687 / Claude Code 2.1.220 / iTerm2 3.6.11。
本書の技術的事実は、公式ドキュメント・BTTバイナリの逆アセンブル・実測のいずれかで裏取り済み（推定箇所は「未確認」と明記）。

---

## 1. 全体アーキテクチャ

```
┌─ ターミナル（iTerm2 / Terminal / Claude Desktop）─────────────┐
│  Claude Code CLI ×N セッション                                  │
│   └─ hooks（イベント駆動・async・非ブロッキング）                  │
│        UserPromptSubmit / PreToolUse / PostToolUse → busy       │
│        Notification（message判別: permission/input）→ waiting   │
│        Stop / SessionStart → idle    SessionEnd → 削除          │
└──────────────┬───────────────────────────────────────────────┘
               ▼ cc-hook.py（stdin JSONを状態ファイルへatomic書き込み）
   ~/.claude/btt/sessions/<session_id>.json
     { state, cwd, tool, pid, term_guid, waiting_kind, started_at, ... }
               ▲
   ~/.claude/btt/render/<name>.json   ← cc-render.py（常駐・1秒間隔）が
               ▲                        全ウィジェットぶんをまとめて計算
┌─ BetterTouchTool ─────────────────────────────────────────────┐
│  Shell Script Widget ×13（1秒間隔, /bin/bash:::-c）             │
│   └─ . cc-widget.sh <name>  … render/<name>.json を読むだけ     │
│        （bashの組み込みのみ。外部プロセスを起動しない）            │
│  status / perm-allow,always,reject / cmd-0..3 / menu-1..5      │
└───────────────────────────────────────────────────────────────┘
```

**全ウィジェットが 642（シェルスクリプトウィジェット）**である点が重要。
629 のプレーンボタンは表示条件を持てず、BTT のアプリ限定は AppleScript から
設定できない（§6.2）ため、「ターミナル以外がフロントなら隠す」は
ウィジェット側の自前判定でしか実現できない。

設計原則:
1. **hooksは絶対にセッションを壊さない** — 全hookは `async: true`、スクリプトは失敗しても常に正常終了。
2. **表示はプル、状態はプッシュ** — hookが状態を書き、BTTが1秒ごとに読む。BTTへの逆方向AppleScript呼び出しは同期処理（ボタン生成）のみ。
3. **設定はファイル編集だけで完結** — `commands.json` 保存→1〜2秒で自動反映。BTT UIの操作は不要。

## 2. 状態モデル

```
        UserPromptSubmit
  idle ────────────────► busy ◄─┐
   ▲                      │     │ PreToolUse / PostToolUse（ツールごと）
   │ Stop                 │     │
   │                      ▼     │
   │                   waiting ─┘  Notification
   │                      │        waiting_kind = permission | input
   └──────────────────────┘
  SessionEnd → 状態ファイル削除（hard kill時は発火しないため pid生存確認でsweep）
```

- **PostToolUse → busy が重要**（レビューで判明した最大の欠陥）: これが無いと、許可プロンプトにキーボードで答えた後もツール実行が終わるまで `waiting` のまま残り、応答ボタンが「回答済みプロンプト」に対して表示され続ける。
- **Notificationはpermission専用ではない**: 60秒アイドル通知でも発火する。payloadの `message` に "permission" を含むかで `waiting_kind` を判別し、応答ボタンは `permission` のときだけ出す。
- **`waiting` は2つの意味を持つ。判定に使うときは必ず `waiting_kind` まで見る**:

  | `waiting_kind` | 意味 | ユーザーの操作 | 緊急度 |
  |---|---|---|---|
  | `permission` | 許可プロンプトが出ている | 必要 | 高 |
  | `input` | 60秒アイドル通知が飛んだだけ | 不要 | ゼロ |

  state だけで扱うと逆向きの失敗が出る。実際に (a) 放置しただけのセッションが
  実行中のセッションを最大1時間隠し（§3）、(b) アイドル通知を挟んだ次のターンで
  経過時間が前ターン起点になっていた（`started_at` を「waiting からの復帰＝同一
  ターン継続」と一律に扱っていたため）。維持してよいのは `permission` からの復帰だけ。
- **stale判定は時刻ではなくpid生存確認**: hook環境には `CLAUDE_PID`（CLIのpid）が入っている（実測確認）。`os.kill(pid, 0)` で生存確認し、死んでいれば状態ファイルを削除。時刻ヒューリスティック（旧900秒）は「強制終了したbusyを15分表示」「20分ビルド中を偽idle」「数時間の正当なwaitingを偽idle」と3方向に誤るため廃止。
- **pidだけでは足りない — 開始時刻も併せて照合する**: pid は再利用される。強制終了（SessionEnd未発火）後にその pid が別プロセスへ割り当てられると `os.kill` が成功し、**状態ファイルが永久に消えず実在しないセッションの ⏳ が残る**。hook が `ps -o lstart=` を控え（pid変化時のみ）、読み出し側が照合する（60秒キャッシュ）。**`LC_ALL=C` 必須** — lstart はロケール依存で、記録側（ターミナル環境を継承）と照合側（BTTから起動）で書式が変わると、生きているセッションを消してしまう。
- **`session_id` が無い payload では書き込まない**: 共通の `unknown.json` に落とすと、複数セッションが同じファイルを奪い合い「pid は A、state は B」という混ざった record ができる。表示されない方が安全。

## 3. 複数セッションの表示選択

旧実装の「mtime最新」は、busyセッションのPreToolUse連打がwaitingセッションを恒常的に隠す（実環境でwaiting 2.5時間のセッションが隠されていた）。

**v1（実装済み）: 優先度順 + バッジ**
```
permission > busy > waiting/input > idle（同順位は updated_at 降順）
他にアクティブなセッションがあれば「+N」を表示
```
**`waiting` を一律で最優先にしないこと**（§2）。ここで「waiting > busy」を採った
動機は許可待ち2.5時間が隠された件だが、それは `permission` にのみ当てはまる。
`input`（60秒アイドル通知）にまで同じ優先度を与えると、**放置しただけの
セッションが20分ビルド中のセッションを最大1時間隠す**という逆向きの同じ失敗になる。
描画側が `input` を idle と同格に扱っているのとも揃える。

**v2（将来）: フォーカス追従** — hook環境の `ITERM_SESSION_ID`（`w0t1p0:GUID` 形式、実測確認）を状態に記録済み。実測コスト: osascriptでiTerm2のアクティブセッションGUID取得 ~300ms（毎秒は不可）、`lsappinfo front` ~6-9ms（毎秒可）。本命はiTerm2 Python APIのAutoLaunchデーモン（~20行）が `FocusUpdate` 購読でGUIDをファイルに書き、ウィジェットはそれを読むだけ（イベント駆動・ポーリングゼロ）。フォーカス解決失敗時はv1にフォールバック。

## 4. 表示ウィジェット

- BTT Shell Script Widget（type 642）。実行設定 `BTTShellScriptWidgetGestureConfig` は `launchPath:::引数` 形式（逆アセンブルで確定。例 `/bin/bash:::-c`）。スクリプト本体キーは `BTTTouchBarShellScriptString`。
- **AppleScriptで作成した642ウィジェットはBTT再起動まで実行されない**（実測）。インストーラは最後にBTT再起動を行うこと。
- 出力JSON: `text` / `background_color` / `font_color` / `hidden` 等（キーはバイナリ内ドキュメントで確認）。
- トークン表示は**コンテキスト充填率%**を主表示にする。「163k」という絶対値は窓が200kか1Mかで意味が真逆になるため（163k = 200k窓の82%(危険) / 1M窓の16%(余裕)）。分母は `settings.json` の model 名に `[1m]` が含まれるかで判定（transcript内のmodel名には `[1m]` が現れないため settings 参照が必要）。
- transcript末尾読みは実測0.22ms/回で問題ないが、(mtime,size)キャッシュを併用しモデル名とトークンは1パスで取得。

## 5. 操作系

### 5.1 スラッシュコマンド（keyword map方式・実装済み）
`~/.claude/btt/commands.json` の `buttons` 配列がそのままTouch Barボタンになる。
- `label`（表示: 省略形・愛称自由）/ `command`（実際の入力）/ `enter` / `enabled` / `color`
- `cc-render.py` が毎秒mtimeを監視し、変化があれば `cc-sync.py` が差分同期（追加/更新/削除）。
- ボタン実体: 642ウィジェット。**主アクションは 137（非同期ターミナルコマンド）で
  `cc-menu.py run <i>` を呼ぶだけ**。押下記録・0.35秒の一拍・Return 送信・メニュー印は
  すべて Python 側で行う。BTT のアクションでは条件分岐が書けず「送ってよい状態か」を
  送信直前に確認できないため（経緯は §12.3）。
- **642 は新規作成時に BTT 再起動が必要**（629 は不要だったが、表示条件を持てないため §12.2 で移行した）。

### 5.2 許可プロンプト応答ボタン（実装済み）
- スクリプト駆動ウィジェット（642）で、`waiting_kind == "permission"` のときだけ表示する（`hidden: true` はBTTがサポート、バイナリ内ドキュメントで確認）。
- 送信はフロントアプリへのキーストロークではなく、状態ファイルに記録した `term_guid` に対して **iTerm2 AppleScript `write text` でセッション直接送信**（tty直書きなのでフロントアプリ非依存。escは文字コード27）。送信直前に対象セッションが今もwaitingかを再確認する。
- 注意: 1/2/escというキー割り当ては公式ドキュメントに明記がない（実挙動ベース）。CLIのUI変更で壊れる可能性を許容し、`commands.json` と同様に外部設定化しておく。
- **ラベルを固定にしないこと（§16）。** 実際の選択肢はツールごとに違い、
  `AskUserQuestion` では任意の N 択になる。固定の `2 常に許可` を出したまま
  押させると、表示と違う項目が選ばれる（実機で発生）。外部設定化は
  `permissions.json` で実施済み。

> この方式は、旧実装（グローバルなキーストローク送信）が
> 「プロンプトが出ていない時に押すと入力欄に文字が入るだけ」
> 「ターミナル以外がフロントの時に押すと**別アプリに入力される**」
> の2つを起こしたことへの対処。**同じ誤りをコマンドボタン／番号ボタンでも
> 繰り返した**（§12.3）ので、送信系を追加するときは必ずこの節に戻ること。

## 6. 配布・パッケージ化（→「プラグインで配信できるか」への回答: **できる**）

2つの成果物に分けて配布する:

### 6.1 Claude Code側 = 公式プラグイン
プラグインはhooksを同梱でき、**利用者のsettings.jsonを編集せずに**有効化と同時にhookが動く（公式ドキュメントで確認）:
```
claude-touchbar/
├── .claude-plugin/plugin.json      # メタデータ
├── hooks/hooks.json                # 本書§2のhook配線（コマンドは ${CLAUDE_PLUGIN_ROOT}/scripts/… を参照）
└── scripts/cc-hook.py など
```
- `${CLAUDE_PLUGIN_ROOT}`（プラグインdir）/ `${CLAUDE_PLUGIN_DATA}`（永続データ）が環境変数として渡る。状態ファイルの置き場は `${CLAUDE_PLUGIN_DATA}` に移すのが正道。
- 配布: gitリポジトリをマーケットプレイスとして `/plugin marketplace add <repo>` → `/plugin install claude-touchbar`。スコープは user / project / local / managed。

### 6.2 BTT側 = .bttpreset ファイル
- エクスポートはAppleScript `export_preset "プリセット名" outputPath "…" compress false` で自動化可能（sdefで確認）。
- フルエクスポート形式のトップレベルは `{BTTPresetName, BTTPresetUUID, BTTGeneralSettings, BTTPresetContent:[…]}` で、`BTTPresetContent` は**アプリ単位のコンテナ配列** `{BTTAppBundleIdentifier, BTTAppName, BTTTriggers:[…]}`（Global疑似アプリは `BT.G`）。
- **アプリ限定トリガーは AppleScript からは作れない**（2026-08-02 実測で確定。旧版に「コンテナJSONを渡せば作れる（逆アセンブルで確定）」と書いていたのは**誤り**）。フルエクスポートのトップレベルが `BTTPresetContent: [{BTTAppBundleIdentifier, BTTAppName, BTTTriggers:[…]}]` というアプリ単位コンテナ配列であることは事実だが、**それを作る経路が API に無い**。試した3通りはすべて読み戻すと `BTTBelongsToApp: "Global"` になる:
  1. トリガーJSONに `BTTBelongsToApp` を入れて `add_new_trigger` → Global
  2. アプリコンテナごと `add_new_trigger` → Global（戻り値が UUID でなく `missing value`。コンテナを「トリガー」として解釈できず、中の `BTTTriggers` だけ拾っている挙動）
  3. 作成後に `update_trigger <uuid> json '{"BTTBelongsToApp":…}'` → 成功応答は返るが Global のまま（キー自体が保存されず読み戻しで消える）

  `add_new_trigger` の sdef に app 系パラメータは存在しない（`parent_uuid` と `shared_secret` のみ）。残る経路は **`.bttpreset` の import か BTT UI での手動移動**の2つ。
  → 本実装は**アプリ限定を使わず、642ウィジェット側の自前判定で隠す**（§12）。
- 利用者の取り込みは `open xxx.bttpreset`（ダブルクリック可、CFBundleDocumentTypes登録済み）または `btt://import_preset/`（アンダースコア。ハイフン版は存在しない）。
- インストーラ（シェルスクリプト1本）: ① プリセットをimport ② `defaults write com.apple.touchbar.agent PresentationModeGlobal appWithControlStrip` ③ `killall ControlStrip` ④ BTT再起動（§4の制約）。

## 8. 既知の制約・リスク

- 許可プロンプトの 1/2/esc キー割り当ては非公式（ドキュメント未記載）。CLI更新で変わり得る。
- Touch Barの物理幅: コントロールストリップ併存時は表示領域が限られる。ボタンが増えたらBTTグループ（type 630, 子は `parent_uuid` で追加）に畳む。他アプリ用のボタン群と同居する場合、**互いにフロント判定で隠し合う**のが幅の解（§12.2）。
- 自前のフロント判定には**更新間隔ぶんの隙**がある（1秒）。ボタンが見えている状態で Cmd+Tab して押すと旧フロント向けの操作が新フロントに飛ぶ。常時居座りは消えるが誤爆の完全な解ではない（原理的に消すには BTT ネイティブのアプリスコープが要るが、API から設定できない）。**送信系は必ずセッション直接送信にして、この隙を無害化する**（§12.3）。
- `statusLine` 機能（40+フィールド: model / context_window / cost / rate_limits 等をstdinで受け取れる）は、将来transcript解析を置き換えられる有力な代替。ただしユーザーが独自statuslineを使い始めた場合の共存設計が必要なため現段階では未採用。
- Claude Desktopアプリのセッションもhooksは同様に発火するが、`term_guid` が無いためフォーカス追従の対象外（優先度選択には乗る）。

## 10. Phase 3.1: フォーカス追従とpeersセッション対応（2026-08-02）

### 追加: cc-focus.py（ステータスウィジェットのタップアクション）

ステータスウィジェット(6304089B)に type 137（非同期ターミナルコマンド）で配線。
注意度順（permission待ち > 入力待ち > busy > idle、同格は更新降順）に対象を選び、
iTerm2 の該当セッション/タブ/ウインドウを select して前面化する。
iTerm2 が既にフロントで先頭候補がアクティブなら次の候補へ巡回（連打でループ）。

### 発見: server:claude-peers セッションにはキー送信が効かない

デスクトップアプリ/claude.ai 駆動のセッションは CLAUDE_PID が
`claude ... server:claude-peers` プロセスを指す。このプロセスの
ITERM_SESSION_ID はサーバー起動時に継承した環境の残骸で、実際の UI は
アプリ側にある。つまり term_guid のタブに write text しても読む相手が
いない（実際には caffeinate が前面のタブに「1」が打たれていた）。

対応:
- cc-hook.py: pid 変化時に `ps -p CLAUDE_PID -o command=` を確認し
  `ui: "peers" | "tty"` を状態ファイルに記録
- cc_common.session_host(): peers は com.anthropic.claudefordesktop 扱い
  → 1/2/esc ボタンは TUI セッションのみに表示される（自動で非表示化）
- cc-send.py: TUI 候補優先。peers 待ちのみなら open -b でアプリ前面化
  （アプリ内の承認ボタンは外部から押せない。前面化が上限）
- cc-status.py: peers の許可待ちは「🔐 App許可待ち」表示

### 未解決

## 12. Phase 3.3: 描画のデーモン化と表示条件の自前化（2026-08-03）

### 12.1 毎秒 python3 を起動していた問題（CPU 58% → 6%台）

BTT の Shell Script Widget は**ウィジェットごとに毎秒プロセスを起動する**。
9 ウィジェットがそれぞれ python3 を叩いていた時点の実測（10回平均）:

| 実行するもの | 実測 |
|---|---|
| `python3 -c pass`（起動のみ） | **47.5 ms** |
| `lsappinfo` × 2（`front_bundle()` の中身） | 16.9 ms |
| `cc-widget.sh`（旧・ステータス） | 103.6 ms |
| `cc-btn.py`（旧） | 84.6 ms |
| `cc-menu.py show N`（旧） | 43.8 ms |
| `cat`（参考） | 7.4 ms |

合計 **576 ms/s ＝ コア1個の 58%** を常時消費。うち 380 ms/s（66%）は
「インタプリタが起動するだけ」で、表示内容の計算ではなかった。とくに
`CC menu 1`〜`5` は 45 秒 TTL の機能のために常時 219 ms/s を燃やしていた
（印が無ければ即 hidden を返すので、ほぼ全部が起動コストの空振り）。

**対処**: 計算を常駐プロセス `cc-render.py` に1本化し、各ウィジェットは
`cc-widget.sh` が `render/<name>.json` を読むだけにする。

- 読み手は **bash の組み込みのみ**（`read` / `printf` / `kill` / `:`）。
  外部プロセスを起動しないので **3.7 ms/回**
- BTT の起動形は `bash -c` なので、**`source` で読む**こと。
  `/bin/bash script.sh` にすると bash が2プロセスになり 3.7 → 7.0 ms に倍増する
- `front_bundle()` と `load_sessions()` はティックあたり1回だけになる
  （以前はウィジェットごとに独立実行）

結果は **13 ウィジェット × 3.7ms + lsappinfo 16.9ms + デーモン自身 ≒ 67 ms/s（約 6.7%）**。
ウィジェット数は増えているのに約 8.6 分の1。

**bash の罠**: `read` は**区切りに当たらず EOF を踏むと非ゼロを返す**。変数には
入っているので、`if read -r l < f && …` と書くと改行で終わらないファイルを
毎回「読めなかった」と誤判定する（pid ファイルでこれを踏み、毎秒デーモンを
起動しに行っていた）。書き手側で改行を付け、読み手は**戻り値を見ない**。
`2>/dev/null` は**入力リダイレクトより先**に置くこと（後ろだとリダイレクト
失敗のメッセージが素の stderr に出る）。

**生存管理**: launchd は使わない。ステータスウィジェットが `render/.seen` を
毎秒触り、pid が死んでいたら起動し直す（二重起動は flock で弾く）。逆に
`.seen` が 15 秒止まったらデーモンは自分で終了する（BTT 終了後に常駐が
残ってバッテリーを食うのを防ぐ）。さらに**自分のソースの mtime を監視し、
変わったら終了する** — chezmoi apply でスクリプトを差し替えても常駐したまま
だと古いコードを実行し続けるため（実際にこれで嵌まった）。

### 12.2 コマンドボタンを 629 → 642 に変更

629 プレーンボタンは**表示条件を持てない**。ターミナル以外を操作している
ときも居座り、Touch Bar の幅を食い、押すと別アプリにスラッシュコマンドが
入力されていた。BTT のアプリ限定が AppleScript から使えない（§6.2）以上、
**642 ウィジェットにして自前で隠す**しかない。

- 実行設定 `BTTShellScriptWidgetGestureConfig` は**トリガーのトップレベル**に置く
  （`BTTTriggerConfig` の中だとスクリプトが一切実行されず、再起動しても直らない）
- 幅キーは型ごとに別: **629 は `BTTTouchBarButtonUseFixedWidth` + `BTTTouchBarButtonWidth`、
  642 は `BTTTBWidgetWidth`**
- 押下フィードバックを追加。入力→Return の間に 0.35 秒の無反応があり、そこで
  二度押しされると `/usage/usage` のように 2 回入力される（実際に発生した）。
  押下時に `press.json` を書き、cc-render が 0.6 秒だけ色を明るくする
- **送り先が解決できないときも隠す**。フロントがターミナルでも「Claude が
  動いていないタブ」なら押しても意味が無い。*押せるのに何も起きない*は
  *出ない*より悪い（ユーザーは壊れたと判断する）

**642 化だけでは誤爆は消えない**（査読で指摘されて判明）。表示判定は毎秒なので、
ボタンが見えている状態で切り替えられると押下が新しいフロントに飛ぶ — 窓が
「常時」から「1 秒」に縮むだけである。実際に塞げるのは §12.3 の送信側の修正で、
642 化はその前提条件にすぎない。

### 12.3 送信を全部「セッション直接書き込み」に統一する

`BTTPredefinedActionType: 193`（カスタムテキストを入力）は**押した時点で
フロントにいるアプリへ打ち込む**。これをコマンドボタンと番号ボタンの両方で
使っていた。穴は3つ:

1. 対象が既にその状態でなければ（メニューが閉じている等）**素の文字列が
   プロンプトに入る**
2. 表示判定は毎秒なので、**ボタンが見えている状態で切り替えて押すと別アプリに入る**
3. **宛先が2系統あった**（査読で発覚）。コマンド文字列はフロントのアプリへ、
   メニューの印は `pick_for_front()` が選んだセッションへ行くため、一致する保証が無い。
   フォーカス中のタブが Claude の動いていないシェルだと、`/model` はそのシェルに
   入って `command not found` になり、印は**別の生きているセッション**を指す。
   45 秒間その別セッション向けに番号ボタンが出て、押すと数字がそこに入る
   — **メニューはどこにも開いていないのに**

これは §5.2 で許可応答ボタンについて一度直した設計への逆行だった。番号ボタンだけ
先に直したときも、同じ穴がコマンドボタン側に残っていた（同じ誤りを2回踏んでいる）。

**対処**: 主アクションを両方 `137` にして `cc-menu.py run <i>` / `send <n>` を呼ぶ。
送り先は `cc_common.target_session()` に一本化し、**文字を送る相手と印を付ける
相手を定義上一致させる**。Python 側で送信直前に全部確認する:

- 印が有効か（TTL 45 秒）
- **印を書いたあとに、そのセッションで実際に何かが起きていないか**（下記）
- 番号が選択肢の範囲内か
- 送り先 GUID が記録済みで、そのセッションがまだ生きているか

どれか欠けたら**何も送らない**（誤爆より無反応を選ぶ）。ただし 137 の stdout は
どこにも表示されないので、**理由は `menu.log` に残す** — 無反応の理由が残らないと
ユーザーから見た挙動は「壊れている」と区別がつかない。

#### 失効判定に `updated_at` を使ってはいけない

「印より後に対象が busy になったか」で切ると、**メニューを開いた後に一往復して
idle に戻った場合を素通りする**（45 秒以内に普通に起きる）。かといって状態を
問わず `updated_at` の変化で切るのも誤り: `cc-hook.py` は hook のたびに無条件で
`updated_at` を書き、**60 秒アイドルの Notification はユーザー操作なしに発火する**。
TTL 45 秒の内側で発火すると、メニューが開いたままなのに番号ボタンが消える。

正しい信号は **transcript の (size, mtime) スナップショット**（`cc_common.transcript_stamp`）。
実ユーザーのターンでは必ず追記されるが、アイドル通知では書かれない。これで
「タイマー起因の hook」と「実際の活動」を、状態を分類せずに切り分けられる。
transcript が取れないセッション向けに、旧来の busy チェックを二段目に残す。

印は**送信のあと**に書く。コマンド自体が transcript を動かす場合に、直後の判定で
自分の書き込みを「活動」と見て自滅しないため。

#### 残る限界

「メニューを開いて Esc で閉じ、**セッションに一切の変化を起こさないまま**番号を押す」
は検知できない。TUI の画面を読まない限り原理的に無理。ただしこのとき被害は
**正しいセッションのプロンプトに数字が 1 文字入るだけ**で、打ち消し可能。

### 12.4 その他の実測（domdom-inspector セッションとの相互検証）

- **`BTTAdditionalActions` は保存時に `BTTActionsToExecute` に正規化される**別名。
  入力はどちらでもよいが、`get_triggers` は常に後者を返す
- **`BTTPredefinedActionType: 264`（キー送信）は主アクションでは保存されない**。
  必ずアクションシーケンスの要素として持たせる
- **Esc には専用アクション `189`** がある（キーコード 53 を 264 で送るより確実）
- `BTTBelongsToApp` は `"Global"` 以外の値（`"Trash"` など）を取り得るが、
  API から書き込むことはできない
- **cc-sync は自分の印を持つ孤児ボタンを掃除する**。state ファイルが失われたり
  途中で失敗した回があると BTT 側にだけボタンが残るため（SCHEMA 変更をまたいで
  実際に残っていた）。state の永続化は掃除より**先**に行う（順序を逆にすると
  掃除で落ちたときに作成済みボタンの uuid を見失い、次回それらが孤児になる）

### 12.4.1 BTT ネイティブの条件付き表示は「どれも API から設定できない」（確定）

「自前判定をやめて BTT の機能で条件表示できないか」を 3 方向から潰した結果を
記録しておく（将来の再調査を防ぐため）。**結論: 自前判定が唯一のプログラマブルな手段**。

| 候補 | バイナリ内の実在 | AppleScript から | 結果 |
|---|---|---|---|
| アプリ限定トリガー（`BTTBelongsToApp` / アプリコンテナ） | あり | **不可**（3通りとも Global に落ちる） | §6.2 |
| 条件付きアクティベーション（`BTTTriggerConditions` / `…Data` / `…Format`、変数は `BTTActiveAppBundleIdentifier` 等） | あり | **不可**。`update_trigger` は成功応答を返すが**読み戻すと全キーが消える**。条件は `BTTTriggerConditionsData` に NSKeyedArchiver の base64 で入る想定で、文字列形式は受け付けない | BTT UI で組むしかない |
| 「変数が真のときだけ表示」 | `BTTMenuItemVisibleIfVariableIsTrue` / `…IsFalse` | — | **Floating Menu 専用**。Touch Bar 側に同等キーは無い（`BTTTouchBarVisible` / `BTTTBVisibleGroupBeforeSleep` は用途が別） |

**将来の選択肢: Floating Menu への移行**。Floating Menu なら
「App Did Activate(671) / Did Deactivate(672) で変数を書く → 変数が真のときだけ表示」
が組めるため、**ポーリングを原理的にゼロにできる**。許可応答ボタンや番号メニューの
ように「特定の状況でだけ出したい」ものは、Touch Bar より素性が良い可能性がある。
現状の毎秒ポーリング（13 ウィジェット × 3.7ms）は許容範囲なので着手していない。

### 12.4.2 フロント判定の共有について（見送り、条件付きで再検討可）

複数プロジェクトのウィジェットが Touch Bar に同居すると、各自が
`lsappinfo`（16.9ms）を叩いて重複コストを払う。こちらのデーモンはどのみち
毎秒 1 回計算しているので `render/front` に公開できるが、**共有は見送った**。
理由は失敗モードが悪いこと: デーモンが `kill -9` でファイルを残したまま
落ちると値が固まり、**エラーも出ないまま「ボタンが二度と出ない」**状態になる。

鮮度チェックが難しいのは、BTT の起動形が `/bin/bash`（macOS は 3.2）で
`$EPOCHSECONDS` も `printf '%(%s)T'` も使えず、現在時刻を得るのに `date` の
プロセス起動が要るため（削減幅が消える）。

**時計を使わない解はある**: 読み手が自分のスタンプファイルを持ち、
bash の組み込みである `[ a -nt b ]`（mtime 比較）で判定する。

```bash
if [ "$SHARED/front" -nt "$MY_STAMP" ]; then   # 前回の自分の実行より後に書かれた
  IFS= read -r fb 2>/dev/null < "$SHARED/front"; : > "$MY_STAMP"
else                                            # 書き手が止まっている → 自前で取る
  fb=$(lsappinfo info -only bundleID "$(lsappinfo front)")
fi
```

この形にするなら、書き手は**値が変わらなくても毎ティック書く**必要がある
（本実装の「変わった時だけ書く」最適化の対象外にする）。採用する相手が
現れたときに実装する。

実行中の経過秒は TUI 自身が出しており、⏳ が見えている時はたいてい
ターミナルが前面＝重複する。**60 秒を超えたときだけ**添え、平常時は空いた枠に
**実行中のツール名**を出す（`⏳ Bash · S6 W8`）。Touch Bar は幅が限られるので
「他で見えている情報は出さない」を原則にする。

## 13. 共有スロット基盤の設計判断（2026-08-03・未実装）

Touch Bar に複数プロジェクトが同居し始めた（macenv 13 ウィジェット /
domdom-inspector 6 / local-ui-builder 4）。実機で右端が切れており、しかも
番号メニュー 5 個は普段隠れているので、`/model` を押した瞬間にさらに 5 枠要る。
「iTerm / Chrome / IDE / Claude App ごとに柔軟に対応したい、Mac/Ubuntu 両方で」
という要件に対する設計。**決定のみ記録。実装は未着手。**

### 13.1 方式: 1ボタン=1トリガー をやめ、汎用スロット + 宣言にする

- 幅だけ決めた**無名スロットを 8〜10 個**だけ BTT に置く（全プロジェクト共用）
- 常駐デーモンがフロントアプリを**毎秒1回だけ**判定し、該当パネルの内容を流し込む
- 押下は `run <slot>` の1系統。動作は宣言（`shell` / `keystroke` / `open-url` / `send-to-session`）
- `panels.json` に「アプリ bundle id → パネル」「パネル → ボタン列」を書く

狙い: **アプリ／ボタンの追加が JSON 編集だけで済む**（BTT 操作ゼロ・再起動なし）。
コストがスロット数で固定される（参加プロジェクトが増えても `10 × 3.7ms + 16.9ms ≒ 54ms/s`）。

**Ubuntu 対応の観点から、この方式は選択肢ではなく必然**（下記 13.4）。

### 13.2 決定事項（実装前に確定させたもの）

1. **`render/*.json` の契約から色を外し、class（意味名）にする。** waybar は
   `background_color` を受けず `class` + CSS で色を当てるため。`cc-status.py` の
   `build()` は既に `("busy"|"waiting"|"idle"|"none", text)` を返し `render()` で
   初めて RGB に変換しているので、**意味名は既にある**。載せる位置を変えるだけ。
   これをやらないと Ubuntu 対応が「リーダー差し替えだけ」にならない
2. **ステータス表示はスロット化しない。** 内容で幅が変わる（`⏳ Edit 4m08s S9 W9 · ⚠️ctx73%`）
   ため固定幅スロットでは切れる。かつ一番読まれるウィジェット。**ボタンだけスロット化**する
3. **押下の安全性は「世代照合」ではなく「不変条件」で担保する。**

   まず**世代照合は原理的に成立しない**。押下側が持つ情報はスロット番号だけで、
   BTT のアクションは静的な文字列（`run <slot>`）なので、「ユーザーが見た時点の
   世代」を受け取る手段が無い。押下時に `slot-N.json` を読めば常に最新＝自分自身と
   一致するため、チェックとして機能しない。厳格にしようとすると逆に
   「内容が更新された直後の押下が黙って捨てられる」だけになる（status は毎秒動くので
   頻度は低くない）。

   達成可能な最良は次の**不変条件**:

   > **同一パネル内では、あるスロットのアクションの束縛を変えない。**
   > 表示（text / class）は毎ティック変えてよいが、**アクションは変えない。**

   これが守られていれば、世代がいくつズレていても「見たもの＝実行するもの」は
   構造的に一致する。チェックではなく設計で保証する。

   そのうえで実効性があるのは**フロントアプリの再解決**（ファイルが記録している
   パネルと、いま前面のアプリから解決されるパネルが違えば no-op）。⌘Z のような
   破壊的キーが別アプリに飛ぶのを防いでいるのはこちら。

   **この不変条件が静かに破れる経路が3つある。実装前に全部塞ぐこと。**

   **(1) `panels.json` のホットリロード。** 「JSON 編集だけで反映（再起動なし）」が
   設計の狙いなので `cc-render` は mtime を見て再読込する。すると**パネル名は同じまま
   スロットの意味が変わる**瞬間ができ、パネル*名*に紐付いた不変条件をすり抜ける。
   → パネル同一性を **(パネル名 + 設定世代)** にする。`panels.json` を読み直したら
   世代を1つ進め、押下時に世代が違えば no-op。**これは毎ティックの世代とは別物**で、
   変わる頻度が桁違いに低い（編集時のみ）ため「更新直後の押下が捨てられる」問題は
   起きない。捨てられるのは「編集した瞬間に押していた場合」だけで、それは捨ててよい。

   **(2) スロットの詰め直し。** 同一パネル内でボタンが実行時に出入りすると
   （例: 許可待ちのときだけ応答ボタンを出す）、**詰め直した瞬間に後続スロットの束縛が
   全部ずれる**。「hidden にするだけだから安全」と思って実装しがちなので明示する。
   → **hidden にするスロットは位置を保持し、絶対に詰めない。** パネルのボタン列は
   固定長で、変わるのは可視性だけ。幅は無駄になるが、束縛の安定と引き換えなら安い。

   **(3) 番号メニュー**: `/model` のときスロット2＝Opus、
   `/effort` のときスロット2＝Med と、同じスロットの意味が変わる。ここだけは束縛を
   固定できないので、押下時に「**どのメニューが開いていたか**」の同一性を照合する
   （世代番号ではなくメニュー識別子）。`cc-menu.py` の印の確認が実質これに当たる。
   **スロット化する際は「番号メニューだけは例外」と明示的に書くこと** — 後から読む人が
   「なぜここだけ複雑なのか」で迷うため

   なお `tick`（13.3）は**デーモンの生死を測るためのもの**で、この話とは目的が別。混同しない。
4. **鮮度チェックで degraded 表示 + 押下拒否**（13.3）
5. **所有関係**: スロットは macenv が提供し、他プロジェクトは `panels.json` に宣言を
   置くだけ。**macenv 未導入の環境では何も出ない**（各プロジェクトは現行実装への
   フォールバックを持つ）。インストール順で壊れないようにするため

**明示的に受け入れるトレードオフ**: 現状は各プロジェクトが自分のトリガーを所有して
いるので、他が壊れても自分は動く。共用スロット + 単一デーモンにすると
**macenv のデーモンが死ぬと全プロジェクトが死ぬ**。これは暗黙に混ぜず、選んだ損失として記録する。

### 13.3 鮮度チェック: 「均一に固まる」ではなく「見えて壊れる」

デーモンが死んだとき、表示が固まるだけでは**「古い」ようにしか見えず「壊れている」
ようには見えない**。しかも押すと `slot-N.json` に残った**古いアクションが実行される**
（ユーザーには効いたように見え、実際には数分前のパネルの動作が走る）。これが最悪の形。

**実装は二層**:

- **押下拒否は Python 側**（`run <slot>`）で `render/tick` の mtime を見て古ければ拒否。
  最悪の形はここだけで閉じる
- **表示の degraded は読み側**（bash）。ただし **macOS の `/bin/bash` は 3.2.57 で、
  `printf '%(%s)T'`（4.2+）も `$EPOCHSECONDS`（5.0+）も使えない**（実測）。
  `[ a -nt b ]` は使えるが**秒精度**で、読み手もデーモンも毎秒動くため境界でばたつく。
  → **時計を使わずティックカウンタで数える**。デーモンが `render/tick` に単調増加の
  整数を毎ティック書き（内容が変わらなくても書く）、読み手は前回値と比較して
  「同じ値が K 回続いたら degraded」。文字列比較と整数演算だけで組み込みに収まる

実装時の注意（査読由来）:
1. **tick は「1ティックぶんの描画を書き終えた最後」に更新する。** 別スレッド/別タイマーで
   書くと「デーモンは生きているがレンダラが `lsappinfo` で固まっている」を検知できず、
   ticker だけ元気に回って機構が丸ごと無効化される
2. **初回起動時に degraded を出さない**（前回値が無い状態を「変化なし」と数えない）
3. **K は 3 以上**。ウィジェットの更新間隔とデーモンのティックは独立なので、1〜2回の
   取りこぼしは正常範囲

### 13.4 Ubuntu: waybar の制約が方式を決める

| 事実（公式 man `waybar-custom.5` で確認） | 設計への影響 |
|---|---|
| **モジュールは config に静的宣言のみ。実行時追加の機構が無い** | **スロット固定数が必然。**1ボタン1トリガーのままでは載らない |

### 13.5 実装前に把握しておく実測（peer 3セッションとの相互検証）

  `get_triggers trigger_app_bundle_identifier` が追加前後で0件のまま）
- **`BTTShellScriptWidgetGestureConfig` が必須なのは 642 固有。** 629 + 137 では

### 13.6 ボタン押下の検証方法（実タップ不要）

**`execute_assigned_actions_for_trigger <UUID>` で押下を再現できる。**
`trigger_action <UUID>` では**再現できない**うえ、**両方 `missing value` を返すので
戻り値では区別できない**（これで「BTT がスクリプトを実行していない」と誤判定しうる）。

実セッションを巻き込まない手順:
1. 検証用の iTerm2 ウインドウ（ただのシェル）を作り GUID を取る
2. そこを指す偽セッションを `waiting`/`permission`（優先度0）で置く
3. **`cc_common.target_session()` がその偽セッションを選ぶことを assert** してから実行
4. `contents of session` で画面を読んで到達を確認、後片付け

この手順で §12.3 の修正が実機で動くことを確認済み（`/review` の入力と実行、
`/model` → 番号ボタン描画 → 番号送信、印の自動消去、`menu.log` への記録）。

### 13.7 Touch Bar を複数プロジェクトで共有するときの取り決め（2026-08-05）

macenv / domdom-inspector / local-ui-builder の3者で合意した内容。共有スロット方式に
移行すればスロットは macenv が一元管理するので不要になるが、それまでは各自が独立に
トリガーを作るため、次の取り決めが要る。

**BTTOrder の帯**（重複すると他プロジェクトのボタンが自分のボタンの間に割り込む。実際に発生した）

```
0〜55    macenv    (0-3 コア / 10-13 コマンド / 50-55 番号メニュー)
100〜105 domdom-inspector   (101,106 は将来の復活用に予約)
200〜    local-ui-builder
```

**`BTTNotes` を全ての管理下トリガーに付ける。** 印が無いと棚卸しで「これは誰のものか」を
判断できず、他プロジェクトが触ってよいか分からない（実際に問い合わせが発生した）。
macenv は `cc-touchbar-core` / `-perm` / `-cmd` / `-menu` の4種。

**ユーザーが GUI で作った既存トリガーには触らない。** order 0/1 に `T`（app=Trash、
子アクション 388）と無名（app=Global、子アクション 525）が居る。帯が重なっても
実表示に空きは出ていないので動かさない（動かすと order 7 が埋まっているぶん帯が分断される）。

**`get_triggers` は親トリガーと子アクションを同列に並べて返す。** 子アクションは
`BTTIsPureAction: true` + `BTTTriggerParentUUID` を持ち `BTTTriggerType` が無い。
これを別トリガーとして数えると件数を誤る（上記を4個と誤認した）。棚卸しでは
`BTTTriggerType` の有無で親子を分けること。

**`BTTBelongsToApp` は GUI 由来のトリガーにだけ載る。** `T` は `"Trash"`（ゴミ箱アプリ）に
スコープされているので通常作業では現れない。一方、AppleScript で流し込むと保存時に破棄される
（§6.2）。**アプリ限定が API から設定できないことの5通り目の傍証**でもある。

### 13.8 BTT の地雷（追加・実測）

- **`BTTPredefinedActionType: 128`（アプリを指定してキー送信）を `update_trigger` で
  流し込むと BTT 本体がクラッシュする**（2026-08-05 domdom が実測。以後 `get_triggers` が
  `-609 接続が無効です` を返し続け、`open -a` してもプロセスが常駐しない）。
  復旧はクラッシュ前のダンプから UUID を拾って `delete_trigger`。
  **キー送信は 264 をサブアクションに置く形だけが安全**（264 を主アクションに置いても保存されない）。
- **`get_triggers` は失敗も破損もする。握り潰さないこと。** BTT クラッシュ中は `-609`、
  他プロジェクトのシェル文字列由来で JSON が壊れることもある（制御文字・不正エスケープ）。
  `cc-sync.py` の `sweep_orphans()` は以前 `except: return` で黙って諦めており、**迷子の
  ボタンが溜まり続けるのに誰も気づかない**状態だった。理由を出して次回に回す形に修正済み。
  修正直後の実行で実際に `CC menu 4` / `CC menu 5` の迷子を回収した。
- **差分判定のハッシュには、実際に保存する値を入れる。** `entry_hash(b, i)` のように
  index だけを入れて保存値 `ORDER_BASE + i` を入れないと、**順序だけを変えたときに
  作り直されず古い並びのまま残る**（local-ui-builder が実機で踏み、こちらにも同じ穴があった）。

## 14. コマンドボタンのグループ化（2026-08-05・実装済み / 常用は非推奨）

`commands.json` の `group` に同じ名前を付けたボタンは、BTT のグループ
（type 630）に畳まれる。子は `add_new_trigger` の `parent_uuid` で結ぶ。
グループの並び位置は「そのグループの最初のボタンが現れた位置」。

実装上の要点:

- **`entry_hash` の basis に親の UUID を入れる。** 入れないと、グループが
  作り直されて UUID が変わったときに子がそのまま残り、**消えたグループに
  ぶら下がったまま**になる（§13.8 の「保存する値をすべて basis に入れる」の一例）
- グループ内の子は `BTTOrder` を 1 から振り直す（トップレベルの帯とは別空間）
- 印は `cc-touchbar-group`。孤児掃除（`sweep_orphans`）の対象に含める

### 14.1 なぜ常用しないか（実機で判明）

**グループ（630）はスクリプトを持てない＝自前で隠せない。** §12.2 で
コマンドボタンを 642 にした理由はまさに「ターミナル以外を操作している間は
消す」ことだったのに、**フォルダだけがその性質を失う**。

実機では、許可プロンプトに答えている最中（コマンドボタンは全て隠れている）に
`レビュー` と `文脈` のフォルダだけが残り、幅を占有し続けていた。中身が
消えて**空のフォルダが残る**形になる。ブラウザ作業中も同様に居座る。

幅を節約するつもりで入れたものが、常時ぶんの幅を払わせる結果になっている。
→ **平らに戻した。** 幅の根本解は §13 の共有スロット方式。

## 15. ブラウザ Web アプリ向けボタン（web-sync・2026-08-05）

Touch Bar から Chrome 上の Web アプリへショートカットキーを送る。定義は
`web-shortcuts.json`、同期と送信は `web-sync.py`。cc-*.py には触れない。

**機構を分けた理由**: 送り先がターミナルではないので、この設計の要である
「セッションへの直接書き込み」（§12.3）が使えない。キー送信に頼る以上、
誤爆を防ぐ層を別に作る必要がある。

- ボタンは Global にしか作れない（§6.2）。素のショートカット送信（264）にすると
  **最前面が何であれキーが飛ぶ**。`Cmd+Z` が別アプリに飛べば実作業が巻き戻る
- そこで本体を 137 にし、送信直前に `web-sync.py send` が最前面の bundle id を
  照合する。外れていれば何も送らない
- **bundle id の照合は casefold で行う。** `lsappinfo` は `com.google.Chrome`
  （C 大文字）を返すが、LaunchServices の既定ブラウザ設定は `com.google.chrome`
  （小文字）。完全一致にすると **Chrome だけ静かに外れる**（§13.5）
- キー送信自体は BTT に投げ返す（`trigger_action`）。osascript から System Events で
  叩くと呼び出し元プロセスに Accessibility 権限が要るが、BTT 経由なら要らない
- 表示判定はウィジェット側の**インライン bash 1 行**（`lsappinfo` 2回・16.9ms）。
  ここで python3 を起動しないこと（起動だけで 47.5ms。§12.1 の教訓）
- 検証は `execute_assigned_actions_for_trigger`（§13.6）。結果は `web-sync.trace` に
  残るので、「BTT が実行していない（ファイル無し）」「対象アプリでないので送らな
  かった（skip）」「送った（sent）」を切り分けられる

### 15.1 開いているページで出し分ける（match・2026-08-15）

**bundle だけでは足りなかった。** 単一の Web アプリ向けのボタンなのに、Chrome が
最前面ならどのページでも出る。ブラウザは 1 日中最前面なので、実質「常時居座り」と
同じ状態になっていた（利用者の指摘: 「使っていないときにでも出てしまう」）。

`match` を書くと URL とタブのタイトルで絞れる。照合対象は
`~/.claude/btt/web-front` の `"<URL>\t<タイトル>"` 1 行。

**URL をウィジェットから直接取ってはいけない（実測）**:

| 方法 | 1 回のコスト |
|---|---|
| `osascript` 起動のみ | 62ms |
| `osascript` 起動 + Chrome へ初回 AppleEvent | 191〜215ms |
| **同一プロセス内の 2 回目以降** | **15ms** |
| 常駐（1 秒間隔）の定常コスト | 20 秒で 0.02 秒 CPU ＝ 1 コアの 0.1% |

2 秒間隔 × ボタン数で回せば前者は 1 コアの 10% を燃やす。§12.1 と同じ結論に
なるので、**常駐 1 本（`web-front.applescript`）に集約し、ウィジェットは
bash 組み込みの `read` で 1 行読むだけ**にした。ウィジェット側の追加コストは実質ゼロ。

- 常駐は launchd（`com.claude-touchbar.web-front`）。**載せる判断は `sync` が持つ**
  — `match` 付きのボタンが 1 つでもあれば載せ、無くなれば降ろす。match を使わない
  利用者の機械に常駐を置き去りにしない
- **`tell application` の前に `is running` を見ること。** 無いと Chrome が起動して
  いないときに勝手に起動する
- 書き込みは値が変わったときだけ tmp→mv。毎秒 read する側に中途半端な行を見せない
- **TCC（オートメーション権限）は責任プロセスごとに別**。ターミナルから叩いた
  osascript は iTerm の許可で通るが、launchd 配下では osascript 自身として
  改めて許可を求める（`Prompting for access to indirect object Google Chrome.app
  by osascript`）。**承認するまで AppleEvent は mach_msg で止まったまま**で、
  エラーも出ない。「常駐は動いているのにファイルが更新されない」ときはこれを疑う
  （`log show --predicate 'process == "tccd"'` で確認できる）
- **押下側にも同じガードを足した。** 表示は最大 1 秒古いので、その隙にタブを
  変えて押されると対象外のページへキーが飛ぶ（Chrome の `Cmd+K` はアドレスバー）。
  ここで Chrome へ問い直すと 200ms 待たせるので、常駐が書いた値を使う
- 常駐が死んでいるとき（ファイルが無い/空）は**隠す側に倒す**。出す側に倒すと
  常時居座りに戻るのに気づけない。状態は `web-sync.py status` に出る
- URL だけでなくタイトルも見るのは、`localhost:3000` が他プロジェクトの dev
  サーバと区別できないため
- **`update_trigger` は `BTTActionsToExecute` を空配列で上書きしても旧サブアクションを
  消さない**（domdom-inspector 側の実測・2026-08-15）。幅・order・ラベル・
  `BTTTerminalCommand`・表示スクリプトは反映されるのにこれだけ残り、残った 264 が
  主アクションと一緒に走って **137 側の照合を素通りしてキーが飛ぶ**。`cmd_sync` が
  delete→add で作り直しているのはこの点でも正しい（更新で済ませないこと）

**ウィジェット周りの実測（出典: domdom-inspector 側のセッション・2026-08-15。こちらでは未再現）**:

- **`refresh_widget` は何もしない。** 実 UUID に 20 回投げてもスクリプトの実行回数が
  変わらない（心拍ファイルで計測）。戻り値は常に `missing value` なので、呼べたことは
  効いた証拠にならない。押下直後の即時反映はできず、更新間隔を詰めるしかない
- **`BTTTouchBarScriptUpdateInterval` は小数を受ける。** 0.3 で実測 3.2 回/秒
- **`hidden: true` を返したウィジェットもポーリングされ続ける。** 一度隠れると戻らない
  という心配は要らない
- **642 の幅は `BTTTBWidgetWidth` 単独では効かない。** 実機写真の before/after で、
  そのキーだけを入れた状態では幅が文字数に比例していた（Auto のまま）。
  `BTTTouchBarButtonUseFixedWidth: 1` + `BTTTouchBarButtonWidth` を足すと揃った。
  ただし**「`BTTTBWidgetWidth` が完全に無効」までは示されていない**（併用時の寄与は
  未検証）。確認手順は issues/2。上の「642 は `BTTTBWidgetWidth`」の記述はここで
  暫定的に否定されている
- **`get_triggers` で読み返せることは「効いている」証拠にならない。** BTT は知らない
  キーもそのまま保存して返す。この幅キーの誤りはそれが原因で生まれた。**描画の判定は
  実機の見た目でしか取れない**

**BTTOrder の帯**（Touch Bar は複数プロジェクトの共有資源。重複すると並びが混ざる）:
`0–55 macenv` / `200–201 local-ui-builder (ここ)` / `300–302 domdom-inspector`。
domdom は平常時 1 個・押すと 3 個に展開するため、伸縮で隣を押し出さないよう最後尾。

## 16. 許可応答ボタンのラベルを実態に合わせる（2026-08-06）

### 16.1 何が壊れていたか

応答ボタンのラベルは `1 許可 / 2 常に許可 / esc 拒否` の**固定**だった。
実際の選択肢はツールごとに違う:

| プロンプト | 実際の選択肢 | 固定ラベルとの一致 |
|---|---|---|
| Bash / Edit 等 | 1 Yes / 2 don't ask again / 3 No(esc) | ○ |
| **AskUserQuestion** | 任意の N 択（+ Other） | **✕ 全く違う** |
| ExitPlanMode | 承認の仕方が別系統の3択 | ✕ |

`AskUserQuestion` でも **`PermissionRequest` は発火する**（実測）。つまり
選択肢プロンプトに対して `2 常に許可` が出ており、押すと**表示と違う項目が
選ばれていた**。ユーザーからの「選択肢が出た時の実態と合わない」はこれ。

### 16.2 選択肢の入手経路は payload しかない

`PermissionRequest` の payload:

```
keys       : cwd, effort, hook_event_name, permission_mode, prompt_id,
             session_id, tool_input, tool_name, transcript_path
tool_input : AskUserQuestion なら {questions: [{question, options:[{label,…}]}]}
```

**hook にしか渡らない。** transcript にもセッション状態にも残らないので、
取り逃すと復元経路が無い。`cc-hook.py` が `perm_options` として控える。

- 質問は順に1つずつ提示されるので**先頭の質問の選択肢だけ**採る
- 末尾の "Other" は含めない（番号が振られるかを実測していない。ずれた番号を
  送るくらいなら宣言された選択肢に絞る）
- ツール名も記録する。以前は `busy` のときしか拾っておらず、許可待ちでは
  捨てていた

**罠: PermissionRequest の直後に Notification が発火して record を上書きする。**
`cc-hook.py` は毎回 `rec` をゼロから組み立てるため、`perm_options` を引き継が
ないと**書いた次の瞬間に消える**。実測では表示中の記録が `tool=""` /
`perm_options` 無しになり、ラベルが既定に戻っていた（直したつもりで直っていない、
という一番たちの悪い形）。許可待ちが続く間は前の値を引き継ぐ。
**この引き継ぎは `if/elif` 連鎖の後ろに置くこと** — 途中に挟むと `elif` が
そちらに結合して Notification の分岐が死ぬ（**構文は通るので compile では
気づけない**）。

### 16.3 表示の割り当て

| 選択肢の数 | 担当 | 理由 |
|---|---|---|
| 0（表で空配列） | 出さない | 実文言が不明なら当てずっぽうより無反応 |
| 2〜3 | 応答ボタン（perm-*） | 色分け（承認=緑/常に=青/拒否=赤）を保てる |
| 4 以上 | 番号ボタン（menu-N） | 専用ボタンが3つしか無い |

番号ボタンの印には出処が2つになった。コマンドボタンの**宣言**（§5.1）と、
`PermissionRequest` が出した**実際の選択肢**。後者は CLI 自身の出力なので
宣言より確かで、TTL も transcript 照合も要らない（`waiting/permission` である
こと自体が「今出ている」を意味し、答えれば PostToolUse が busy に戻す）。

**許可プロンプト中はコマンドボタンを隠す。** 応答ボタンに幅を譲るのと、
答える前に `/clear` のような取り消せないものを押す事故を防ぐため。

### 16.4 送信先の不一致（§12.3 と同じ誤りが許可経路に残っていた）

表示側（`cc-btn.py`）は「フロントアプリに属する許可待ちが**1つでもあるか**」で
出し、送信側（`cc-send.py`）は「**全**許可待ちのうち `updated_at` 最大」へ
送っていた。2つのセッションが同時に許可待ちだと、**見て押したのと違う
セッションに 1/2/esc が入る**。

選択を `cc_common.permission_session()` に一本化し、送信は `send_target()` で
実測して確定する（表示は近似・送信は実測、という他の送信経路と同じ役割分担）。

### 16.5 切り詰めは「文字数」ではなく「cell」で、しかも短すぎてはいけない

`widget_width()` は CJK を 2 cell として数えるので、「12文字まで」で切ると
日本語は 24 cell ぶんになり隣を押し出す。

そして**短すぎる方が危険**。上限 10 cell にしたところ、選択肢
「グループをやめて平らに戻す」と「グループのまま残す」が実機で
`1 グルー…` `2 グルー…` になり、**1 と 2 のどちらを押すか決められなくなった**。
共通の接頭辞を持つ選択肢では、切り詰めは「読みにくい」ではなく
「**選べない**」に直結する。

上限を決めるのは**バー全体の残り幅**であって `BTTTBWidgetWidth` ではない。
この値は下限で、内容が長ければ実際の描画は伸びる（perm-* は 3 つとも 100px で
作られているのに `2 常に許可` = 10 cell が欠けずに出ている）。

**出処ごとに分けること。** 番号ボタンは2つの経路で出るが、混み具合が違う:

| 出処 | 同時に出ているもの | 上限 |
|---|---|---|
| 応答ボタン（最大3個） | コマンドボタンは隠れている | 28 cell |
| 番号ボタン・許可由来（最大5個） | 同上 | 16 cell |
| 番号ボタン・コマンド由来（最大5個） | **コマンドボタン9個が出たまま** | 12 cell |

一方に合わせると他方が溢れる。コマンド由来のラベルは `commands.json` の宣言で
元から短い（`Def` / `Opus`）ので、狭くても実害が無い。

**値は撮影した実機画像から「画素を測って」決める。目分量で余白を読むと外す。**
実際に2回外した。1回目は 20 cell を入れかけて計算で気づき、2回目は 16 cell を
入れて**実機で5個目が 50px 欠けた**。原因はどちらも使用可能域の右端を目で
1880px と読んだこと。実測では **1356px**（そこからコントロールストリップ）。

```
ボタンが使える幅   = 306px 〜 1356px = 1050px ÷ 1.34 px/pt = 784pt
n cell のボタン    = 22 + 9n pt（+ 間隔 4pt）
5個並べたときの総幅 = 130 + 45n pt

  13 cell → 715pt  余白 69pt（状態表示が「🔐 App許可待ち」でも 42pt 残る）
  14 cell → 760pt  余白 -3pt
  16 cell → 850pt  実機で 5 個目が 50px 欠けた
```

測り方: `screencapture -b` の PNG を `sips` で BMP にし、列ごとに「背景より
明るい画素」を数えて連続区間を出す。ボタンの箱がそのまま区間として出るので、
**期待幅（22+9n）と突き合わせれば切れているかが判定できる**。実際 menu-1〜4 は
期待どおり 210〜232px で、menu-5 だけ 148px（期待 198px）だった。
**見た目の印象ではなく、この突き合わせで判定すること。**

**変えたら実機で確認すること。** Touch Bar は `screencapture -b` で撮れるので、
一時的な許可待ちセッションを `sessions/` に置いて描画させれば、実際の
プロンプトを出さずに撮れる（撮ったら必ず消す。§16.6）。

### 16.6 検証方法（実タップなしで、表示中の状態を捕まえる）

許可プロンプトが出ている間は Claude 側の処理が止まるので、自分では観測できない。
**バックグラウンドのサンプラを先に起こしてからプロンプトを出す**:

```bash
# 応答ボタンか番号ボタンが1つでも可視になった瞬間に、
# セッション記録と render/*.json をまとめて書き出す
grep -l '"hidden": false' "$R"/perm-*.json "$R"/menu-*.json && { … }
```

これで「ラベルが既定に戻っている」「`perm_options` が消えている」を客観的に
掴めた。ユーザーの目視報告だけだと、*なぜ*そう見えるのかまでは分からない。

デーモンの描画経路そのものは、`cc_common.load_sessions` /`front_bundle` を
差し替えて `render_all()` を直接呼べば、実セッションにも Touch Bar にも触れずに
全ウィジェットの出力を一度に確認できる。

**見た目（幅が収まっているか）は `screencapture -b` で撮れる。** Touch Bar は
非対話モードなら撮影できるので、判定を人の目に委ねる必要は無い。

```
sessions/ZZZ-probe.json に waiting/permission + perm_options を置く
  → デーモンのティックを待つ（~2.5秒）
  → screencapture -b -x tb.png
  → **必ず消す**（try/finally。置きっぱなしにすると応答ボタンが出たままになる）
```

- `pid` を持たない記録は `updated_at` が新しければ 900 秒生存する（`load_sessions`）
- **フォーカスを奪わないこと。** ターミナルが前面でなければボタンは出ないが、
  `osascript ... activate` で前面に出すとユーザーの作業を横取りする。前面に
  戻るまで待つ
- probe が出ている間に押されても無害。送信側は `send_target()` で実フォーカスを
  再解決し、そこが許可待ちでなければ何も送らない（§16.4 の修正がそのまま効く）
- **撮れた ≠ 写っている。** Touch Bar は消灯するので、描画が正しく出ていても
  真っ黒な PNG が撮れる（実際に踏んだ）。撮影後に明るい画素があるかを検査して、
  無ければ撮り直すこと。この検査が無いと「16 cell で 5 個目が欠ける」ような
  実害を、真っ黒な画像を見て見逃す
- 空振りの原因は3種類あり、区別しないと誤診する:
  **(1) ターミナルが前面でない**（表示条件を満たさない・仕様どおり）
  **(2) probe の GUID がフォーカス中のものと違う**（`pick_for_front` の絞り込みで落ちる）
  **(3) Touch Bar が消灯**（描画は出ているが写らない）。
  render/*.json を見れば (1)(2) と (3) を切り分けられる

## 17. アプリ別ネイティブ Touch Bar 素通し（2026-08-09）

The Boosters（Electron 製・v0.22.0 で自前の NSTouchBar を実装）が前面のとき、
BTT のバーではなくアプリ自身の Touch Bar を出したい、という要求への対応。
前提事実: **BTT は前面アプリが自前の NSTouchBar を持っていても既定では自分の
バーで上書きする**（実測: dev 版 Electron 前面でも BTT バーが残る。§17.3）。

BTT にはこのための正規機能「アプリ別 TouchBarBehavior = Show App Default
Touch Bar」がある（設定 UI: Touch Bar タブでアプリを選択）が、例によって
AppleScript から直接は設定できない。実測で確定した投入経路と保存の全体像:

| 項目 | 実測結果 |
|---|---|
| 投入経路 | `.bttpreset` の `import_preset`（アプリコンテナの `BTTAppSpecificSettings`）。§6.2 の「アプリ単位コンテナは preset import でしか作れない」の実用例 |
| JSON キー | **`BTTTouchBarMode`**。UI バインディング名の `TouchBarBehavior` で書くと import 時に**黙って破棄される**（エラーは出ず、既定値の行ができる） |
| 値 | **3 = Show App Default Touch Bar**。0=既定 / 2=BTT 全幅（Control Strip も消える）/ 1=可視変化なし（用途未特定） |
| 保存先 | data store の **AppSpecificSettings エンティティ（Z_ENT=3）の `ZTOUCHBARMODE1`**。アプリ行（Z_ENT=2）の `ZTOUCHBARMODE` は**読まれていない**（0 のままで素通しが動作することを分離テストで確認） |
| 確認方法 | **export では確認できない**（`BTTAppSpecificSettings` は `BTTDisableGlobalTriggers` しか往復しない）。sqlite の読み取りで確認する（`cc-nativebar.py` の `mode_of()`） |
| 反映 | **BTT の再起動が必要**（import 後のライブ反映はされない） |
| ダイアログ | import は確認ダイアログを出す（Import クリック 1 回。「Import and do not ask again」は選ばない） |

### 17.1 実装

- `native-apps.json` — 対象アプリの宣言（ユーザー編集用）
- `cc-nativebar.py` — 冪等プロビジョニング。設定済みは sqlite 読み取りでスキップし、
  **DB が読めないときは import しない**（同名 preset はマージされず増えるため、
  「分からないなら何もしない」に倒す）
- `run_once_after_80-btt-touchbar.sh.tmpl` から呼ばれる

### 17.2 罠

- **preset の重複 import**: 同じ内容を再 import すると同名 preset が並ぶ。増えた
  preset の削除 API は無い（`delete_preset` は sdef に存在しない）。掃除は BTT UI か、
  BTT 停止中に data store から SQL で削除（**必ずバックアップを取る**。手順は
  presets(Z_ENT=13)・アプリ行(Z_ENT=2)・settings 行(Z_ENT=3)・`Z_2BELONGSTOPRESETS`
  join の 4 点セット）
- **dev 実行の Electron は bundle id が `com.github.Electron`**（パッケージ前は
  electron 本体の Info.plist が使われる）。素通し対象に入れると**全プロジェクトの
  Electron dev アプリが対象になる**ため、意図的に入れていない。dev 版で素通し検証
  してもパッケージ版の設定は検証できない（逆も同じ）
- **「BTT がいてもアプリバーが通った」という目撃は BTT の再起動窓と重なり得る**。
  BTT 停止中〜起動直後はネイティブバーが出るので、素通し検証は BTT が起動しきって
  BTT バーが表示された状態から行う（実際にこの取り違えが起きた）

### 17.3 検証手順（再利用可）

安全な実験台は **Karabiner-Elements Settings**（起動が軽い・NSTouchBar 無し・
実害無し）。素通しが効くと「空のアプリ領域 + Control Strip」に変わるので
BTT バーとの区別が一目でつく。§16.6 と同じく `screencapture -b` で撮って判定:

```
1. 一時 preset（BTTTouchBarMode: 3）を import → ダイアログ承認
2. BTT 再起動（ライブ反映されないため必須）
3. osascript で対象アプリを前面化 → screencapture -b → iTerm2 に戻す
4. 後片付け: BTT 停止 → バックアップ → SQL で 4 点セット削除 → BTT 起動
```

## 18. 配布物化: 状態ファイルの置き場は環境変数で決めてはいけない（2026-08-09）

§6.1 に「状態ファイルの置き場は `${CLAUDE_PLUGIN_DATA}` に移すのが正道」と
書いていたが、**この構成では誤り**。切り出し作業で判明したので訂正する。

理由は**プロセスの親が 2 系統あること**:

```
Claude Code ──> hooks ──> cc-hook.py      状態を「書く」
                                ↓
                    ~/.claude/btt/sessions/
                                ↑
BetterTouchTool ──> ウィジェット ──> cc-widget.sh / cc-render.py   状態を「読む」
```

`${CLAUDE_PLUGIN_DATA}` は Claude Code が hook に渡す環境変数なので、
**BTT が起動する側のプロセスには存在しない**。env で解決すると書き手と読み手が
別のディレクトリを見ることになり、**エラーは一切出ないまま「状態が永久に idle」**
になる（BTT 側は空のディレクトリを読み続けるだけなので、失敗として現れない）。

→ **データ置き場は env に依存しない固定パス**（`~/.claude/btt`）にする。
プラグイン形式で配る場合も、hooks が呼ぶスクリプトの**場所**だけ
`${CLAUDE_PLUGIN_ROOT}` にして、**書き込み先は固定**にする。`cc-hook.py` が
`BASE` を `os.path.expanduser` で持っているのは（偶然だが）この点で正しい。

一般則: **異なる親から起動される 2 つのプロセスが同じファイルで会話する設計では、
その場所を親の環境変数から導出しない。**

### 18.1 配布用プリセットは `export_preset` で作らない

`export_preset` は**プリセット丸ごと**を出すので、利用者個人のトリガー（Trash 用の
ボタン、クリップボードマネージャ等）まで公開物に混入する。`BTTNotes` の印で
自分のトリガーだけを拾って組み立てる（`tools/export-preset.py`）。
**実ホームパスが残っていないかを書き出し後に検査する**こと。

### 18.2 共有 settings.json への hooks 追加は「存在の保証」で

丸ごと置換すると利用者が足した `permissions.deny` が無警告で消える（§2026-08-08 の
知見と同じ）。dict は再帰・list は和集合・スカラーは触らない、で足すだけにする。
検証は「他ツールの hook と deny を置いた settings.json に 2 回適用して、
どちらも生存し重複も増えないこと」で行う（実施済み）。

## 19. 幅不足の実測と、スロット化では解けない部分（2026-08-09）

§13 の共有スロット基盤は「幅不足の根本解」として起票していたが、**幅を実測した
結果、平常時の超過はスロット化では解けない**ことが分かった。記録しておく。

使用可能域は 784pt（§16.5 の画素実測）。ボタン1個は `22 + 9×cell` pt（+間隔 4pt）。

| 状況 | 必要幅 | 判定 |
|---|---|---|
| 平常時（status + コマンド9個） | **989pt** | +205pt 超過。**7個目 `code-rev` から右端で欠ける** |
| `/model` 押下時（+ 番号5個・改修前） | **1398pt** | +614pt 超過 |
| 番号メニュー中はコマンドを隠す（改修後） | **651pt** | 収まる（余裕 133pt） |

**スロット化は物理幅を増やさない。** 同時に見せたいものが 10 個あるなら、
スロットが 10 個あっても同じだけ幅を食う。スロット方式の利点は
「複数プロジェクトが**それぞれ**トリガーを持つ重複を無くす」ことと
「waybar のようにモジュールを実行時追加できないサーフェスに載せられる」ことで、
**1 プロジェクト単体の詰め込み過ぎは解決しない**。

### 19.1 実際に効いた対処

1. **排他表示**: 番号メニューが開いている間はコマンドボタンを隠す
   （許可プロンプト中に隠すのと同じ理由・同じ実装）。これで **1398pt → 651pt**。
   幅だけでなく「番号を選ぶつもりで `/clear` に触れる」事故も消える
2. **溢れを黙って切らない**: `cc-sync.py` が同期のたびに幅を計算し、
   **何個目から切れるか**を名指しで出す（`warn_overflow`）。Touch Bar は
   溢れても無言で右端から欠けるので、ユーザーには「ボタンが消えた」としか
   見えない。実際に「右端が切れている」という報告になった
3. **平常時の 205pt 超過は設定で解く**。9 個は入らない（6 個まで）。
   ラベルの短縮は §11 で「フルワードにして誤爆を減らす」と決めた判断と
   衝突するので、**使わないボタンを `enabled: false` にする**のが筋

### 19.2 起票の教訓

「幅が足りない → 枠組みを作り直す」と設計に飛ぶ前に、**幅を数えるべきだった**。
数えていれば、5 行の排他表示で 614pt が消えることと、残りは設定の問題であることが
先に分かった。§13 の設計自体は Ubuntu 対応（waybar）と複数プロジェクト管理では
依然として有効なので破棄はしないが、**「幅不足の根本解」という位置づけは誤り**。
